# Literature matrix (CA-4 format)

Columns follow the CA-4 template. "Read" says how much of the source was read; only the PDFs in `papers/` were opened in full or in part.

| Reference | Problem | Method | Dataset / workload | Metrics | Key finding | Limitation | Relevance to this study |
|---|---|---|---|---|---|---|---|
| Baumann et al., "A fork() in the road", HotOS 2019 | fork() is slow and unsafe in modern systems | Argument plus measurements of fork cost on Linux | Processes with growing mapped memory | fork time vs memory, page-table copy | fork cost grows with the parent's mapped memory (Fig. 1) | Position paper; one machine | Motivates measuring fork() against parent size (H2) |
| Drepper and Molnar, NPTL, Red Hat 2003 (2005 revision read) | Make Linux threads fast and scalable | 1:1 thread design, kernel support (futex, clone) | Creating up to 100,000 threads | Thread creation time | 100,000 threads: 15 min to 2 s | Old hardware; 2005 text says some limits are out of date | Explains why Linux threads are cheap to create |
| Sysel, "A comparison of processes and threads creation", AISC 1294, 2020 | Compare creation time of tasks in Linux | clone() flags explained; C programs timed with clock_gettime | Create a task, with and without a 4 GB address space | Creation time | fork 34 to 94 us (parent) and 60 to 170 us (child); pthread_create 94 to 260 us; fork at 4 GB about 20 ms, thread 170 to 290 us; fork+exec 700 us and more | One laptop, CPU frequency varies; creation only, no pools, task length, memory or runtimes. Read in full (postprint) | Closest prior work for H1 and H2; this study adds task length, pools, memory, runtimes |
| Bendersky, "Launching Linux threads and processes with clone", blog 2018 | Cost of launching a process vs a thread | C micro-benchmark, 10,000 launches averaged | Parent heap size varied | Launch time | About 35 us (process) vs 5 us (thread) at 2 MB; process time grows with heap, thread time does not | Blog, not peer reviewed; C only; no task length, pools, memory or runtimes | Closest earlier measurement of H2 |
| Zhao, Gong, Fonseca, "On-demand-fork", EuroSys 2021 (abstract only) | fork() cost of setting up virtual memory (page tables) for large processes | Kernel change: copy-on-write page tables | Memory-intensive and latency-sensitive applications | fork latency | Page-table copying is a concern even at hundreds of MB; On-demand-fork is faster | Needs a modified kernel; PDF not downloaded | Independent support for the page-table explanation of H2 |
| Voegele, Thomas, Hoenig, "Spork", HotOS 2025 (abstract only) | fork() is slow and complex; programs do not migrate to posix_spawn | Emulation layer removing fork | Legacy software in Linux distributions | Compatibility (84% of software) | Fork can be removed for 84% of existing software | Not a performance study | Recent view that fork is costly |
| Ousterhout, "Why threads are a bad idea", USENIX ATC 1996 | Threads are hard to use correctly | Design argument | None | None | Prefer events for most purposes | Pre-dates modern multicore | Design side of the trade-off (isolation, complexity) |
| von Behren, Condit, Brewer, "Why events are a bad idea", HotOS IX 2003 | Reply to Ousterhout for servers | Argument plus user-level threads server | Web server | Throughput | Threads can match events when implemented well | Prototype scale | Supports comparing thread and event-driven servers |
| Pai, Druschel, Zwaenepoel, Flash, USENIX ATC 1999 | Efficient web server architecture | Event-driven server with helpers | Web traces | Throughput | Event-driven design gives high throughput | One architecture, 1999 hardware | Server architecture background (Sec. 8.7) |
| Welsh, Culler, Brewer, SEDA, SOSP 2001 | Well-conditioned Internet services | Staged event-driven architecture | Web and mail services | Throughput, latency under overload | Stages with queues avoid overload collapse | Complex to program | Alternative to thread-per-request |
| Boyd-Wickizer et al., "Linux scalability to many cores", OSDI 2010 | Does Linux scale on 48 cores | Run kernel-heavy apps, fix bottlenecks | MOSBENCH apps | Throughput vs cores | Most bottlenecks fixed with small kernel changes | 2010 kernel and hardware | Background for kernel-level scaling limits |
| Lozi et al., "The Linux scheduler: a decade of wasted cores", EuroSys 2016 | Scheduler leaves cores idle | Tracing tools, bug analysis | Kernel make, TPC-H | Runtime | Degradation of 13% to 24% on typical workloads (13% make, 14% to 23% TPC-H) | NUMA servers | Scheduler effects on thread and process scaling |
| Li, Ding, Shen, "Quantifying the cost of context switch", ExpCS 2007 | True cost of a context switch | Micro-benchmarks | Cache-heavy workloads | Switch time, cache effects | Indirect cost can be larger than direct cost | Old CPUs. | Context-switch measurements (Sec. 8.7) |
| Litton et al., "Light-weight contexts", OSDI 2016 | Isolation within a process | New OS abstraction (lwC) | Server workloads | Switch time, overhead | Cheap in-process isolation | Needs kernel changes | Shows isolation without full process cost |
| Agache et al., Firecracker, NSDI 2020 | Fast, light virtualization | MicroVM design | Serverless workloads | Boot time, memory | Boot in ms with small footprint | Different level (VMs) | Context for lightweight isolation |
| Hoefler and Belli, SC15 | Rigorous parallel benchmarking | Guidelines | None | Reporting | Report variance and conditions | Guidelines only | Basis of the analysis method |
| Kalibera and Jones, ISMM 2013 | Benchmarking with enough repetitions | Statistical method | None | Confidence intervals | Plan repetitions per level of variation | Managed-runtime focus | Basis of repetitions and CIs |
| Heiser, "Systems benchmarking crimes" | Common benchmarking mistakes | Checklist | None | None | Avoid selective reporting | Informal | Used to review this study |
| Gross, PEP 703; Wouters, Page, Gross, PEP 779 | Optional GIL in CPython | Design / criteria | None | None | Free-threaded build officially supported | Documents, not measurements | Defines the free-threaded runtime tested |
